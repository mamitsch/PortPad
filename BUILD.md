# PortPad build and PortMaster reference

Source audit: **2026-09-11**. This is the maintained build reference;
[BUILDING.md](BUILDING.md) retains the former entry point. Commands below run from
the PortPad repository root unless a different directory is stated. Paths such as
`../PortMaster-New` are example checkout locations, not hardcoded requirements.
For actual run results and unresolved issues, see [CURRENT_STATE.md](docs/CURRENT_STATE.md).

## Desktop development

The supported development path is Linux, including Ubuntu under WSL2. The source
uses Linux/POSIX file APIs; a native Windows/macOS build is not provided. Install
prerequisites if absent (this command changes the host, not the handheld):

```sh
sudo apt install build-essential cmake ninja-build pkg-config libsdl2-dev libsdl2-ttf-dev
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build build
ctest --test-dir build --output-on-failure
./build/portpad
```

Required: C++17 compiler, CMake ≥3.16, pkg-config, SDL2 ≥2.0.14 and SDL2_ttf
(development headers/libraries). CMake imposes no explicit SDL2_ttf version floor.
Ninja is selected explicitly here; the ARM64 wrapper falls back to CMake's default
generator if Ninja is unavailable. WSLg or another SDL-supported display is needed
for the interactive window. A physical controller is unnecessary for local tests.

Use a new build directory if the checkout path/generator changes. CMake copies
`assets/` beside the executable, including DejaVu Sans and DejaVu Sans Mono; it
copies `config/` only when `config/keymap.ini` is absent in that build directory.
Reconfiguration preserves that runtime keymap. No CMake install target, CPack
package, toolchain file or project-specific `PORTMASTER_BUILD` switch exists.

```sh
SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy ./build/portpad --smoke-test
ctest --test-dir build -R 'editor|input' --output-on-failure
```

The application accepts no filename argument; its sole optional argument is
`--smoke-test`. That smoke test renders menu, browser and path dialog, then exits.
`editor_render` is the separate test for viewer/editor/keyboard/prompt rendering.
An optional developer screenshot can be generated by the existing test executable:

```sh
SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy PORTPAD_EDITOR_SCREENSHOT=/tmp/portpad-editor.bmp ./build/editor_render_tests
```

This produces BMP, not the PortMaster submission PNG. CTest registers six suites:

| CTest name | Coverage |
| --- | --- |
| browser | Directory sorting, parent navigation, paging and error behavior |
| state | Main menu, lifecycle and scrolling text dialogs |
| input | INI validation, default/custom bindings, virtual SDL controller hotplug |
| editor | Buffer edits, UTF-8, cursor/history/search, line validation, I/O, backups, failed saves, read-only and browser actions |
| editor_render | Dummy-video viewer/editor, scrolling, keyboard, menus/prompts and quit confirmation |
| startup | Packaged-style asset/config lookup and menu/browser/path rendering |

SDL suites use dummy video/audio via CTest. Tests create isolated temporary files;
they do not need a physical gamepad. Permission-denied directory checks are skipped
when the test process has privileges to read mode-000 directories. Tests do not
establish real firmware compatibility or power-loss resilience.

## Target and compilation model

Initial release target: Linux aarch64 on R36S/RK3326, logical/window size 640×480.
Desktop targets the host architecture. The PortMaster script runs an **ARM64
compiler inside an ARM64 Docker container**, with `--platform linux/arm64`.
On an x86-64 host this requires Docker's ARM64 emulation; on an ARM64 host it is
native. It is not an x86-host cross-compiler/sysroot workflow.

```sh
./scripts/build-portmaster.sh
```

Docker must be running with WSL integration and ARM64 execution available.
The current user needs Docker access. The script mounts the resolved checkout at
`/workspace`, runs as the host UID:GID, and writes `build-portmaster/portpad`.
The builder image is set in `scripts/portmaster-common.sh`:

```text
ghcr.io/monkeyx-net/portmaster-build-templates/portmaster-builder:aarch64-latest
```

The wrapper invokes CMake with `-DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
-DCMAKE_SKIP_RPATH=ON`, builds in parallel, removes executable RPATH/RUNPATH with
`patchelf --remove-rpath`, runs all six suites, and prints `file`/`readelf` evidence.
The test environment adds the builder's SDL pkg-config libdir to `LD_LIBRARY_PATH`.
That is a builder setting, not a launcher setting.

### Compiler and linker settings

`CMakeLists.txt` requires `-std=c++17` without GNU language extensions. In the
validated GNU ARM64 build, Release contributes `-O3 -DNDEBUG`; SDL pkg-config adds
`-D_REENTRANT`. Debug normally contributes `-g` in the GNU desktop build. These
optimization/debug defaults come from CMake/toolchain, not custom project flags.
No explicit `-march`, `-mcpu`, LTO, sanitizer, warning policy or stripping step is
configured. The resulting ARM64 ELF is PIE and not stripped in the observed build;
PIE is a toolchain result, not an explicit portable project requirement.

Default CMake builds `portpad_state` and `portpad_ui` as static project libraries;
`portpad` links them plus the imported SDL2/SDL2_ttf pkg-config targets. This does
not statically bundle SDL or libc. In the current builder pkg-config injects
`-Wl,-rpath,/usr/local/lib -Wl,--enable-new-dtags` despite `CMAKE_SKIP_RPATH`; the
post-link patchelf step removes that build-only search path from the app.
The packaging screenshot harness alone uses `-Wl,--wrap=SDL_RenderPresent`.
For effective commands use `ninja -C build-portmaster -t commands portpad`
(read-only command listing on the host), or inspect `build-portmaster/build.ninja`.
Do not rebuild that ARM64 cache with the desktop host compiler.

### Runtime dependencies and ABI

The verified executable requires GLIBC_2.17 and GLIBCXX_3.4.26. Recheck every
release; the mutable builder tag can change these requirements. Its direct
`DT_NEEDED` entries are SDL2, SDL2_ttf, libstdc++, libgcc_s, libc and the aarch64
loader (`ld-linux-aarch64.so.1`). Font/image/math/thread libraries may appear as
transitive dependencies in `ldd`; that is not a list of libraries to copy.

Firmware must provide SDL2 ≥2.0.14, SDL2_ttf and their dependencies. **PortPad
bundles no shared libraries.** Do not ship SDL2, libc, libstdc++, pthread, GL/EGL/GLX,
Mesa or other core system/graphics libraries, nor replace firmware libraries.
Any future missing non-core dependency needs evidence from `ldd` on the target
firmware and its own license. PortPad's current validator rejects all extra shared
libraries. These restrictions follow the reviewed
[upstream agent guidance](https://github.com/PortsMaster/PortMaster-New/blob/79e6ff94b3c1aeeae930fec6525328ea6bc49d75/AGENTS.md).

No Qt/GTK/Electron, X11-specific app API, Python runtime, gptokeyb input process or
runtime download is used. An SDL library itself may support desktop X11 backends;
that is distinct from a direct X11 application dependency.

## Source layout, export and installable ZIP

PortPad keeps authored launcher/metadata under `portmaster/`, not a copy of
PortMaster's tools. The staging script creates this complete source tree:

```text
dist/portmaster-source/port/portpad/
├── port.json
├── README.md
├── screenshot.png
├── gameinfo.xml
├── PortPad.sh
└── portpad/
    ├── portpad
    ├── libs.aarch64/             (empty)
    ├── assets/fonts/
    │   ├── DejaVuSans.ttf
    │   └── DejaVuSansMono.ttf
    ├── config/keymap.ini
    └── licenses/
        ├── LICENSE.PortPad.txt
        └── LICENSE.DejaVu.txt
```

`./scripts/stage-portmaster.sh` rebuilds/tests ARM64 and recreates that staging
root; manual copies/directories are unnecessary. Its screenshot harness renders
the real browser with a development/software-renderer label and converts it to
640×480 PNG. No cover is authored. The complete staged tree is exported to
**`ports/portpad/`** in an external official checkout. The website calls the source
container `port`; the checkout/scripts actually use `ports`. Keep those contexts
distinct. Required source metadata/artwork/launcher follow the
[official packaging guide](https://portmaster.games/packaging.html).

For other ports, upstream names must start with a lowercase letter or digit and
then contain only lowercase letters, digits, periods or underscores. Launcher/data
names must not conflict with another port. These are upstream naming rules; the
values below are PortPad-specific.

Source naming is case-sensitive: `portpad`, `portpad.zip`, `PortPad.sh`.
`port.json` uses version 4, `name: portpad.zip`, `items: ["PortPad.sh", "portpad"]`,
`items_opt: []`, `attr.arch: ["aarch64"]`, `attr.runtime: []`, `min_glibc: "2.17"`,
`rtr: true`, `exp: true`, `availability: full`, genre `other`, porter `mamitsch`.
No runtime squashfs needs mounting. `gameinfo.xml` references `./PortPad.sh` and
`./portpad/screenshot.png`; those are paths relative to the installed Ports area,
not a standalone command to resolve from the metadata file's parent directory.

The **release ZIP**, after the official builder transforms the source, contains:

```text
dist/portpad.zip
├── PortPad.sh
└── portpad/
    ├── portpad
    ├── port.json
    ├── portpad.md
    ├── gameinfo.xml
    ├── screenshot.png
    ├── assets/fonts/DejaVuSans.ttf
    ├── assets/fonts/DejaVuSansMono.ttf
    ├── config/keymap.ini
    ├── licenses/LICENSE.PortPad.txt
    └── licenses/LICENSE.DejaVu.txt
```

There is no enclosing `port/` or `ports/` in the ZIP. The official builder moves
metadata/artwork into the data directory and renames README.md to portpad.md.
Empty `libs.aarch64/` is omitted. Eleven files are expected; source files, test
executables, logs and build tooling must not enter this archive. The flat license
directory covers PortPad (MIT) and both DejaVu fonts.

## Official release workflow

Host prerequisites: Bash, Docker, Git, Python 3, wget, unzip and usual GNU file,
checksum and comparison utilities. The builder provides compiler/CMake/CTest,
pkg-config, binutils/readelf, file, patchelf, jq and ImageMagick convert/identify.
Python and image tools are development dependencies only. Initial image retrieval
and each official preparation step require network; installed PortPad works offline.

For a new external checkout (the destination must not already exist):

```sh
git clone --depth 1 --filter=blob:none --sparse https://github.com/PortsMaster/PortMaster-New.git ../PortMaster-New
git -C ../PortMaster-New sparse-checkout set tools
git -C ../PortMaster-New switch -c portpad-packaging
./scripts/package-portmaster.sh ../PortMaster-New
./scripts/validate-portmaster-package.sh
./scripts/list-portmaster-package.sh
./scripts/test-portmaster-launcher.sh
```

For an existing checkout skip clone/sparse/switch if already configured. The
repository must have official origin `PortsMaster/PortMaster-New`, include `tools/`
and be outside PortPad. Use a separate port feature branch. Read its current
AGENTS.md before exporting. The wrapper does not create commits, push or submit PRs.
Do not vendor, fork into PortPad or reimplement the upstream release tools.

`PORTMASTER_REPO` may supply the external path instead of the positional argument.
With neither, packaging/export fails with usage; the historical argument-free
example only works when this environment variable is set.
`./scripts/export-portmaster.sh ../PortMaster-New` performs only build/stage/export.
It creates `ports/` itself and records `.portpad-export.sha256` outside PortPad;
an existing unowned/edited target is refused. Do not delete that guard to overwrite
someone else's changes. Amend PortPad's authored inputs and export again.

The packaging wrapper creates the external `releases/` and `runtimes/` directories,
then runs, from the external checkout root, exactly:

```sh
tools/prepare_repo.sh
python3 tools/build_release.py --do-check
python3 tools/build_release.py
```

It copies `releases/portpad.zip` back to `dist/portpad.zip`, writes
`dist/portmaster-revision.txt`, and runs the local validator. It also retires an
old distinct `dist/PortPad.zip` as `PortPad.zip.obsolete`. The staged ELF dependency
report is `dist/runtime-dependencies.txt`. Never substitute a manual ZIP of the
launcher and payload for the source/export/official-check workflow.

### Validation boundaries

The supplemental validator checks ZIP integrity, exact filenames/duplicates,
metadata fields, screenshot dimensions, symlinks, payload equivalence to staging,
aarch64 ELF, dynamic-library allowlist, declared glibc baseline, lack of RPATH,
builder `ldd` resolution and dummy-video startup. It prints GLIBCXX requirements
but does not enforce a separate maximum GLIBCXX version. It needs the corresponding
staging tree and Docker, not only the ZIP. `list-portmaster-package.sh` needs host
unzip and only prints contents. Official `--do-check` checks source packaging.

Launcher tests use isolated fake PortMaster helpers and a stub executable, including
paths containing spaces, execute-bit repair, stdout/stderr logging, application
exit status, missing binary and cleanup. They do not exercise real CFW helper
implementations or every launcher failure branch.

### Repeating and recording a release

Record the PortPad commit **and any uncommitted changes**, builder image ID/digest,
tool versions, external checkout revision, logs, and final archive SHA-256. Useful
existing-tool commands (from PortPad root, after a build):

```sh
git rev-parse HEAD
git status --short
docker image inspect ghcr.io/monkeyx-net/portmaster-build-templates/portmaster-builder:aarch64-latest --format '{{.Id}} {{json .RepoDigests}}'
git -C ../PortMaster-New rev-parse HEAD
sha256sum dist/portpad.zip
```

Use a fresh checkout/build directory and the recorded inputs for release
reconstruction; generated directories are ignored by Git. Do not rely only on
PortPad's HEAD when the implementation is still uncommitted. The existing scripts
hardcode a mutable image tag and official preparation downloads latest metadata:
**the current pipeline is repeatable but does not guarantee byte-for-byte
reproducible releases**. Image pinning, dependency/input snapshots and deterministic
archive timestamps remain planned work; no unimplemented digest override is
advertised here. Leave or remove the temporary official checkout outside PortPad
afterward; do not publish sparse-checkout-generated aggregate release files.

## Launcher, paths, permissions and logging

The shipped launcher is `portmaster/PortPad.sh`, a Bash script with LF endings.
PortMaster launch scripts and gptokeyb mapping files must use LF. The editor
accepts CRLF text but preserves its ending convention; it does not convert such
files to firmware-compatible LF automatically.
Keep submitted launchers at mode 0644, source directories at 0755, and the port
binary at 0755. Staging/export enforce those modes; runtime also calls
`chmod +x ./portpad`, since extraction may lose execute bits. Host helper scripts
under `scripts/` must be executable. This distinction supersedes the old plan's
instruction to mark the submitted launcher executable.

Do not transplant host paths or assume all firmware uses `/roms`. The launcher
resolves its own directory through `BASH_SOURCE[0]` and checks these candidates
in order, selecting the first with `control.txt`:

1. Existing `controlfolder` environment value.
2. `/opt/system/Tools/PortMaster`.
3. `/opt/tools/PortMaster`.
4. `$XDG_DATA_HOME/PortMaster`, with fallback `$HOME/.local/share` for XDG_DATA_HOME.
5. `PortMaster` beside the installed launcher.
6. `/roms/ports/PortMaster` as the final compatibility fallback.

It sources `control.txt`, optionally `mod_${CFW_NAME}.txt`, and calls `get_controls`.
The data directory is first `<launcher directory>/portpad`; only when absent and
`directory` is supplied does it fall back to `/${directory#/}/ports/portpad`.
It checks the binary, changes into that directory, restores its execute bit,
redirects stdout/stderr to `portpad/log.txt`, exports
`SDL_GAMECONTROLLERCONFIG="$sdl_controllerconfig"`, calls
`pm_platform_helper "$GAMEDIR/portpad"`, runs `./portpad`, then calls `pm_finish`
and returns the application status. No kill trap, custom controller emulator,
LD_LIBRARY_PATH override, bind mount or runtime installation is added by PortPad.
Firmware helpers may set further environment/backend settings; the application
uses SDL's selected backend rather than forcing X11/KMSDRM.

Application fonts and default `config/keymap.ini` resolve from `SDL_GetBasePath()`;
the browser resolves `.` from the process working directory. `PORTPAD_KEYMAP`
can override the keymap, with relative values relative to that working directory.
The launcher neither sets nor clears that override. Saves operate at user-selected
document paths with the current process permissions; there is no sudo/privilege
escalation in the application. For other ports requiring privileged helpers,
follow the firmware's `$ESUDO` and binding helpers rather than embedding sudo.

Each launch truncates `log.txt`, logs start time/architecture, captures application
stdout/stderr and logs its exit status. Errors before redirection (missing control
file/binary, directory or chmod failure) are emitted to the caller instead. The
launcher intentionally avoids `set -e`/`set -u` because sourced firmware scripts
are not compatible; host build helpers do use `set -euo pipefail`. Existing
limitations: redirection and platform-helper failures are not explicitly handled,
and early control/get_controls failures exit before `pm_finish`. These are code
review findings, not changes made by this documentation update.

## Installation and hardware checks

Copy the generated `dist/portpad.zip` to the installed PortMaster's `autoinstall`
directory, run PortMaster and return to Ports/Tools. Refresh the frontend or reboot
if needed; the user-reported R36S baseline appeared in Ports after reboot. Launch
PortPad and verify browser, controller, editor/save/backup, read-only confirmation,
suspend/resume and return to the frontend on Quit. Do not copy the source staging
tree or the old capitalized ZIP instead of the release artifact.

If autoinstall consumes a ZIP without installing files, inspect PortMaster's log;
PortPad's log cannot exist before its launcher runs. For launch failures inspect
`portpad/log.txt` and the caller's output. Diagnose missing libraries with `ldd
./portpad` on the actual device before proposing any non-core additions.

The baseline installation, launch, browser, controller mappings and cleanup were
reported validated on an R36S. Exact CFW/version was not recorded in that success
report, so it does not establish separate passes for both ArkOS and dArkOS.
Editor hardware testing is pending. Required broader release coverage remains:

| Firmware | Recorded device status |
| --- | --- |
| ROCKNIX | Pending |
| muOS | Pending |
| dArkOS | Exact firmware/version-specific result not recorded |
| Knulli | Pending |
| AmberELEC | Pending |
| ArkOS | Exact firmware/version-specific result not recorded |

Additional devices/SoCs (RK3566, H700, A133P, Snapdragon 865/662, S922X) and
1024×768, 1280×720, 720×720 (optionally 320×240) remain untested. Check controller
reconnect, firmware SDL/video driver, orientation, display readability and storage
semantics. A builder smoke test or development screenshot cannot establish these.

## Historical context

The initial manually assembled `PortPad.zip` was consumed by ArkOS/dArkOS
autoinstall without installing a launcher/data directory. The implementation was
replaced by official source export/build and later reported working on R36S.
The original plan proposed bundled SDL libraries, `dist/staging/`,
`portmaster/package/.gitkeep` and a `collect-portmaster-libs.sh`; none is the current
implementation. Its full text remains in [PORTMASTER_NEXT_STEPS.md](PORTMASTER_NEXT_STEPS.md).
The original four-suite desktop review remains in
[docs/portmaster-review.md](docs/portmaster-review.md), clearly marked historical.
